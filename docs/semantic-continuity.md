# Semantic Continuity — Why Execution Must Not Sever Semantics

A central ESKA principle is:

> **Execution must not sever semantics.**

This means that when formally represented knowledge becomes operational, the running system should not lose the machine-interpretable meaning that explains what the execution is doing, under which conditions it is valid, and how its result relates back to the governing semantic source.

ESKA is therefore not only concerned with making knowledge executable. It is concerned with keeping knowledge **semantic while it becomes executable**.

## The problem

A common implementation path looks like this:

```text
Semantic model
      ↓ developer interprets it
Application code
      ↓
Execution
      ↓
Result
```

The application may behave correctly, but the semantic connection can disappear during implementation.

For example, an OWL ontology may state that a Margherita pizza is a kind of Vegetarian pizza. A developer can reproduce that conclusion in ordinary code:

```text
if pizza == MARGHERITA:
    vegetarian = true
```

The software can execute, but the runtime system may no longer be able to determine:

- which ontology or semantic model defines the meaning of the classification;
- which semantic Capability the code implements;
- which version of the semantic source governed this particular execution;
- which input and output types belong to the semantic contract;
- under which conditions the Capability is applicable;
- whether the implementation still corresponds to the semantic source after either one changes;
- why a particular Result should be interpreted as a classification result rather than as an arbitrary boolean value.

The execution still works technically, but its semantics have become external knowledge held by developers, documentation, prompts, or convention.

That is what ESKA calls **severing semantics**.

## Semantic continuity instead

ESKA aims to preserve a machine-traceable chain such as:

```text
Semantic Model
      ↓ gives meaning to
Semantic Capability
      ↓ operationalized through
Executable Semantic Knowledge Artifact
      ↓ used by
Execution
      ↓ produces
Result
      ↓ checked by
Verification
      ↓ traceable through provenance to
Semantic source and version
```

The precise executable mechanism is intentionally not fixed by the architecture. It may be an OWL reasoner, SHACL processor, SPARQL engine, DMN engine, OpenMath evaluator, mapping engine, BPMN engine, Java service, Python implementation, or another mechanism.

The requirement is not that every runtime must directly execute RDF. The requirement is that execution remains semantically identifiable and traceable to the formal knowledge and Capability that give it meaning.

## Compilation and generated code are allowed

Semantic continuity does **not** require direct interpretation of the source model.

This is valid:

```text
Semantic Model
      ↓ compile / generate / transform
Executable Artifact
      ↓ run
Execution
      ↓
Result
```

provided the architecture preserves machine-readable relations such as:

```text
Executable Artifact
    operationalizes
        ↓
Semantic Capability

Execution
    uses
        ↓
Executable Artifact

Execution
    uses / is governed by
        ↓
Semantic Model

Result
    was generated by
        ↓
Execution
```

The implementation may therefore be optimized, compiled, distributed, wrapped behind an API, or deployed independently without becoming semantically opaque.

## Provenance is necessary, but not sufficient

Provenance can tell us:

```text
result.json
    wasGeneratedBy
        calculator.py
```

That is useful operational lineage, but it does not by itself explain what the calculation means.

Semantic continuity requires enough additional semantic context to establish something closer to:

```text
Result
    wasGeneratedBy
        ↓
Execution of PizzaAreaCalculationCapability
        ↓
uses executable artifact
        ↓
Pizza area calculation implementation
        ↓
uses semantic model
        ↓
versioned Pizza area calculation model
```

The difference is important:

- **provenance** explains where something came from;
- **semantic continuity** additionally preserves what the operation and its result mean.

ESKA reuses PROV-O for provenance rather than defining a parallel provenance model, while ESKA concepts provide the semantic execution context around that provenance.

## Two dimensions of semantic continuity

The principle has two complementary dimensions.

### 1. Vertical semantic continuity

Meaning remains traceable through the operational chain:

```text
Knowledge
    ↓
Capability
    ↓
Executable Artifact
    ↓
Execution
    ↓
Result
    ↓
Verification
```

Each operational layer remains connected to the semantic layer that explains it.

This allows a machine to ask questions such as:

- What Capability was executed?
- Which semantic model defines that Capability?
- Which executable artifact realized it?
- What source/version governed this execution?
- What Result was produced?
- How was the Result verified?

### 2. Horizontal semantic preservation

Different semantic artifacts have different operational meanings and should not be flattened into an undifferentiated notion of "code":

```text
Ontology        → reason
Knowledge graph → query
Constraint      → validate
Rule            → evaluate
Decision        → decide
Calculation     → calculate
Mapping         → transform
Workflow        → execute
Capability      → invoke
```

An OWL ontology, SHACL constraint, DMN decision, OpenMath calculation, mapping, and BPMN workflow can all participate in execution, but they do not mean the same thing.

A generic function such as:

```text
execute(input) → output
```

may be technically sufficient for runtime dispatch, but it is semantically insufficient if the architecture can no longer distinguish reasoning from validation, decision from calculation, or transformation from workflow execution.

ESKA therefore preserves the semantic kind of the knowledge as well as its operational trace.

## Pizza example

For Pizza classification, the intended chain is conceptually:

```text
Pizza Ontology
      ↓
Pizza Classification Capability
      ↓
OWL reasoning artifact / reasoner
      ↓
Classification Execution
      ↓
Classification Result
      ↓
Verification
      ↓
PROV-O lineage to immutable Pizza semantic source
```

The runtime result is not merely "some data returned by a service." It remains identifiable as the result of a classification Capability whose meaning is grounded in the Pizza ontology and whose concrete execution can be traced back to the exact semantic source used.

The same invariant applies when the execution mode changes:

```text
SHACL       → Validation Capability → Validation Execution
DMN         → Decision Capability   → Decision Execution
OpenMath    → Calculation Capability→ Calculation Execution
SPARQL map  → Mapping Capability    → Mapping Execution
BPMN        → Workflow Capability   → Workflow Execution
```

The mechanism changes. The semantic-continuity requirement does not.

## Why this matters for agents

An agent can call an opaque API if it is told how to do so. But without explicit semantics it may have to reconstruct meaning from names, prose, examples, prompts, or prior conversation.

With semantic continuity, an agent can instead discover machine-described information such as:

```text
Capability
    subject
    inputType
    outputType
    producesRelation
    applicability conditions
    semantic model

Service / Operation
    realizes Capability

Invocation Adapter
    supports semantic request/result representation

Deployment
    supplies the concrete runtime location
```

The agent can then select and invoke an operation because its semantic contract matches the task, rather than because a prompt happened to describe the API correctly.

## Architectural test

A practical way to test the principle is to take a concrete runtime Result and walk backward.

Can the architecture determine, in machine-readable form:

1. which Execution produced the Result;
2. which semantic Capability that Execution performed;
3. which executable artifact was used;
4. which semantic model or models gave the Capability and artifact their meaning;
5. which immutable source/version governed the execution;
6. how the Result was verified;
7. what semantic kind of operation occurred — reasoning, validation, decision, calculation, transformation, workflow, or another explicitly modeled mode?

If the chain stops at "this function/service produced this output," semantic continuity is weak or broken.

If the chain reaches the formal semantic source and preserves the meaning of the operation along the way, execution has not severed semantics.

## Concise formulation

> **Executable knowledge is not knowledge that has been translated into software and then forgotten. It is knowledge whose formal meaning remains an observable, traceable part of its execution.**

In ESKA:

```text
Knowledge
    must remain
Semantic
    while becoming
Executable
```

That is the architectural commitment expressed by:

> **Execution must not sever semantics.**
